# Security

- Runs on Atlassian; no remote service, no egress, no secrets in the app. Scopes are listed with reasons in the README.
- The verdict is plain code (`src/rules/`, pure). Models never decide it. Proposals, Teamwork Graph data and people data have no path into `checkHandoff()`; tests check this.
- Reads of Jira and Teamwork Graph use `asUser()`. The one use of `asApp()` is in `src/validator.ts`: the workflow validator reads the work item (summary, description, labels, components, due date, assignee, project) as the app, because a validator payload carries no user session. There is no fallback to `asApp()` anywhere else: a missing permission is reported, never bypassed.
- A model's proposed decision is kept only if its quote appears word for word in text the caller can read, re-read on the server. A person must confirm it.
- The workflow validator fails closed: it blocks the transition when the check cannot run.
- Rovo MCP access is off until a site admin enables it; tools then act within the calling user's permissions.
- Not covered: the validator can read a work item the person making the transition may not be able to open, and reads decisions as the app (storage is app-wide); the validator's `modifiedFields` ignores description and components, so a description or component edited in the transition screen is not what was checked.
- Not covered: the validator checks that the prepared handoff is Clear, not that its receiver is the current assignee. A reassignment to a different person starts a new handoff record through the trigger, but a transition is not refused on that ground alone.
- Covered since version 10.16: the server checks Jira's "Administer projects" permission, as the person, before it confirms, adds or supersedes a decision or loads or removes samples; a failed check counts as "no". Re-preparing a prepared handoff is limited to its sender, the assignee or a project administrator. Superseding is also limited to the person who confirmed the decision; a decision with no recorded confirmer, such as a sample, can be superseded by any administrator.
- A decision scoped to a label binds only the project it was confirmed in. A label decision confirmed before 2026-11-13 carries no project and keeps binding that label on the whole site until it is superseded.
- Not covered: the evidence check proves that the quote is in the source text, not that the constraints follow from it. A proposal can pair a real quote with a constraint the quote does not state; only the person confirming can judge that, and the panel shows both before Confirm.
- Not covered: `propose-decisions` writes proposals to storage, also when called over MCP. It keeps at most 5 per work item and replaces that item's pending proposals, so a call can displace proposals waiting there. Nothing binds until a person confirms.
- Partly covered: decisions are stored per project with a version check, so one project cannot break another. A single project with a very large number of decisions would still hit the size limit. The old site-wide key is kept, read-only, until the owner confirms the new keys work. The trigger writes a handoff record whenever an assignee changes; the app never writes to Jira, so there is no loop.
- `npm audit` reports vulnerabilities only inside the dependencies of `@forge/react` and `@forge/bridge` (mostly an editor library). The app uses no editor and runs in Forge's sandbox; they can be fixed only by a Forge release.
